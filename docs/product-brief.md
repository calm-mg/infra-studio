# 인프라 스튜디오

상태: 인터뷰 반영안. **제품 결정**과 **구현 제안**을 구분한다. [로그 실습 시안](prototypes/infra-studio-v2.html)은 조작 참고용이지 v0 전체 명세가 아니다. 첫 버전의 검수 대상은 데스크톱 웹이다.

## 제품 결정: 첫 사용자는 무엇을 하러 오는가

새 팀에 합류한 백엔드 개발자가 **기존 서비스가 어디서 실행되고, 요청·데이터·로그가 어디로 가는지 한 화면에서 파악하는 설계 작업대**다. 첫 성공은 예제의 경고를 없애는 것이 아니라, 자기 팀의 구조를 그리고 동료에게 요청 하나의 경로와 아직 모르는 부분을 설명하는 것이다.

- v0: 빈 캔버스나 익명 예제에서 시작해 역할을 놓고, 아는 기술만 지정하고, 자유롭게 연결한다. 로그 수집은 전체 구성의 한 경로다.
- v0: 프런트엔드만으로 설계 파일을 내보내고 다른 워크스테이션에서 다시 연다. 파일 전달은 복사본 전달이지 동기화가 아니다.
- 이후: 변경 전후의 구조적 영향 → 입력값이 있는 수치 시나리오. 로그인 등을 통한 이어하기, Modulith 분리 검토, Terraform 생성은 관심사이지 첫 출시 요건은 아니다.

## 구현 제안: 첫 장면

익명 예제는 `클라이언트 → LB → 서비스 백엔드 → PostgreSQL` 요청 경로로 시작한다. 백엔드는 EC2에서 실행된다. 여기에 `서비스 백엔드 → 로컬 파일 → 수집기 → 로그 저장소` 경로를 그려 요청과 로그를 구별한다. 배치 관계인 ‘EC2에서 실행’은 데이터가 이동하는 선이 아니다.

왼쪽에는 진입점(Gateway·LB), 실행 환경·서비스, 데이터 저장소, 비동기 메시징, 관측(로그·메트릭) 역할을 보여준다. **필수 설치 목록이 아니라 구조를 떠올리는 목록**이다. 없는 역할을 채우라고 경고하지 않는다. 대표 후보에 없는 기술과 같은 역할의 여러 인스턴스도 그릴 수 있어야 한다. 예: ‘서비스 백엔드’와 ‘통계 백엔드’는 같은 역할이나 이름과 연결은 다르다.

오른쪽에는 선택한 대상만 보여준다. 블록은 인스턴스 이름·역할·기술·메모, 선은 방향·관계·설명을 편집한다. 기술을 모르면 비워둔다. 예제 밖의 선도 허용하고 관계를 직접 적을 수 있게 한다. 사용자가 기록한 사실과 도구가 판정한 사실을 섞지 않는다.

### 첫 버전 인수 조건

1. 빈 화면에서 사용자가 서비스 이름을 붙이고, 기술이 미정인 진입점과 DB를 연결한 뒤 요청 경로를 설명할 수 있다. 자유 입력한 기술이나 관계도 남는다.
2. 예제에 통계 서비스를 하나 더 놓고 같은 DB에 연결할 수 있다. 서로 다른 두 서비스와 하나의 공유 DB로 식별된다.
3. 기술 이름을 바꿔도 기존 선은 보존된다. 로그 목적지를 바꿨다고 로컬 파일의 보존 설정이 바뀌지 않는다. 조합을 모르는 것은 ‘미검증’이지 ‘불가능’이 아니다.
4. 노드 삭제 시 연결된 선만 함께 지워진다. 사용자가 적은 구성이 있는데 빈 캔버스·예제·파일 열기로 대체할 때 실수로 작업이 사라지지 않는다.
5. 설계를 내보내 다른 브라우저에서 열면 이름·기술·메모·관계·배치가 복원된다. 깨졌거나 읽을 수 없는 버전의 파일을 열어도 현재 설계는 보존된다.

## 구현 제안: 저장소와 개발 순서

- 같은 저장소에 배포 단위별로 둔다. v0는 `apps/web` 하나이며 로그인·원격 저장 요구가 생길 때 `apps/backend`를 추가한다. 서버 언어나 DB는 지금 정하지 않는다.
- 웹은 Vite + React + TypeScript 앱이다. `apps/web/src/` 아래 `design/`에 설계 문서·편집 연산·파일 형식을, `catalog/`에 역할·기술 후보·예제를, `editor/`에 React Flow 캔버스와 인스펙터를 둔다. 렌더러의 내부 상태를 파일 형식으로 쓰지 않는다.
- 설계 문서는 `schemaVersion`, 안정적인 블록·관계 ID, 양 끝 블록 ID, 표시 좌표를 가진다. 역할과 기술, 인스턴스 이름은 별개다. JSON 파일과 브라우저 마지막 작업 저장에 같은 형식을 쓰는 안을 권장한다. 계정·클라우드·실제 인프라 접근 권한은 필요 없다.
- 첫 개발 단위는 **빈 화면 → 이름 있는 블록 두 개 추가 → 관계 입력 → 내보내기 → 새 세션에서 열기**다. 이 흐름이 통과한 뒤 익명 예제와 관측 경로를 얹는다.
- CI는 기존 Jenkins를 쓰고 파이프라인 정의는 저장소 루트 `Jenkinsfile`에 둔다. 타입 검사·단위 테스트·빌드 후 Playwright로 빌드 결과물을 실제 Chromium에서 검증한다. 단위 테스트는 잘못된 파일을 열어도 설계가 보존되는지, 삭제한 블록의 선만 사라지는지 같은 규칙을 맡는다.
- 첫 브라우저 테스트는 블록 두 개를 연결하고 관계 이름을 입력한 뒤, 다운로드한 설계 파일을 저장 상태가 없는 새 브라우저 세션에서 다시 열어 이름과 연결을 확인한다. 실패 시 Jenkins에 테스트 결과와 실행 추적 파일(trace)을 남긴다. 테스트 데이터는 익명 예제만 사용한다.
- 첫 사용성 검증: 익명 예제를 처음 보는 백엔드 개발자에게 “요청 하나를 따라가고, 통계 서비스가 같은 DB를 쓰는 구성을 추가한 뒤 파일을 건네주세요”라고만 요청한다. 설명이 필요했던 조작과 도식에서 잘못 읽은 관계를 기록한다.

## 이후의 영향 분석에서 지킬 경계

선이 사라졌다는 것은 문서에서 확인할 수 있다. 그것만으로 실제 장애·처리량·사용량은 알 수 없다. 예를 들어 로그를 원격으로 보내는 것과 로컬 파일을 정리하는 것은 다른 동작이다. 디스크 고갈 일수를 계산하려면 남은 용량과 순증가량 등이 필요하다. MAU 증가율은 인프라 교체의 결과가 아니라 부하 시나리오의 입력으로 취급한다.

공유 전에는 팀 정책에 맞춰 예제와 파일을 익명화한다. 제품 검증에는 실제 계정, 호스트 주소, 인증정보, 사내 원본 도면이 필요하지 않다.
